# 项目复盘：求职助手 Agent

## 一、需求来源

我在找 Agent 开发实习，面临 4 个痛点：

1. **信息分散**：BOSS、实习僧各投一遍，没有统一视图
2. **匹配靠感觉**：投了才知道不合适
3. **简历重复改**：每个岗位手动调整，效率低
4. **进度难追踪**：投了 50 家，哪家看了全靠记忆

所以我做了这个 Agent：**把求职流程自动化，从搜索到追踪一站式完成**。

## 二、方案设计

### 整体架构

```text
用户输入
  ↓
ReAct Agent（LLM 自主决策）
  ├── 调 search_jobs → 岗位列表
  ├── 调 get_job_detail → 完整 JD
  ├── 调 match_resume → 匹配分数 + 差距
  └── 调 add_tracking → 加入追踪
  ↓
输出 + 状态保存
```

### 模块划分

| 模块 | 职责 |
|---|---|
| `tools_registry.py` | 工具注册中心，统一暴露能力 |
| `react_agent.py` | ReAct 循环 |
| `state_machine.py` | 投递状态定义 + 转换校验 |
| `storage.py` | SQLite 存储 |
| `tools/` | 具体工具实现 |
| `resume/` | 简历解析与定制 |
| `dashboard/` | Streamlit UI |

**为什么这样分**：

- **工具独立**：每个工具可单独测试，可替换实现（mock → 真实）
- **状态机独立**：转换规则可单元测试
- **Agent 独立**：换 Agent 框架不影响工具层

### 关键设计决策

#### 1. 手写 ReAct 而非用框架

**理由**：

- 面试考"你理解 Agent 原理吗"
- 手写一遍，每环节都能讲清
- 不依赖 LangChain 版本兼容

**代价**：代码多 100 行，需要处理 JSON 解析

#### 2. mock 实现 + 真实实现预留

**模式**：

```python
def search_jobs(keyword, city, limit, platform="mock"):
    if platform == "mock":
        return _mock_search(...)
    elif platform == "shixisang":
        return _fetch_from_shixiseng(...)
```

**为什么**：

- 先跑通链路，不被反爬卡进度
- 接口稳定，换实现只改一个函数
- 面试可讲"我先 mock 验证设计，后接真实平台"

#### 3. 可解释的匹配打分

**不给单一分数**，输出：

- 4 个维度分数（技能/经历/学历/城市）
- 差距列表
- 亮点列表

**为什么**：用户知道往哪优化，不是黑盒。面试时能讲"我设计的匹配算法有 4 个维度"。

#### 4. 简历定制不改变事实

**Prompt 明确禁止编造**，只允许重排、重述。输出包含：

- `changes`：改了什么
- `warnings`：哪些改不了

**为什么**：避免"AI 帮你造假"的风险。面试时能讲"我处理了 AI 内容生成的可信度问题"。

#### 5. 状态机 + 事件表

**投递状态**单独一张表，**事件历史**另一张表。

**好处**：

- 校验合法转换
- 支持统计
- 能画时间线

**面试可讲**："我用状态机管理投递流程，每次变更记录事件，能追溯完整历史。"

#### 6. SQLite 而非 JSON

**理由**：

- 投递记录会长到几百条
- 需要按状态查询
- 支持事件时间线

**面试可讲**："我用 SQLite 存投递记录，支持条件查询和事件追踪。"

#### 7. Chainlit + Streamlit 双 UI

**为什么两个**：

- **Chainlit**：对话式，适合"帮我找岗位"这种 Agent 交互
- **Streamlit**：表格化，适合"批量标记、查看列表"这种管理操作

**面试可讲**："三种交互方式互补：RAG 处理问答、Agent 处理多步任务、Dashboard 处理结构化操作。"

## 三、遇到的问题与修复

### 1. LLM 输出的 JSON 解析失败

**现象**：`json.loads` 报 `Expecting ',' delimiter`。

**原因**：模型在长字符串里用了真实换行。

**修复**：

- Prompt 明确要求用 `\n` 转义
- 加 `json5` 兜底

**效果**：稳定 2 轮完成，不再多走一轮。

### 2. 数据库表未建

**现象**：Dashboard 报 `no such table: job_marks`。

**原因**：`init_db()` 里没调用 `init_marks_table()`。

**修复**：补调用，删旧 DB 重建。

### 3. 状态机非法转换

**现象**：`update_status` 不校验，能把"被拒"改成"约面"。

**修复**：写入前 `validate_transition`，非法抛异常。

### 4. 简历匹配数据格式不统一

**现象**：`resume_json` 有时是字符串，有时是对象。

**修复**：工具里加 `isinstance` 判断。

### 5. Chainlit 步骤输出太长

**现象**：`cl.Step` 输出完整 JSON，屏幕被刷屏。

**修复**：截断到 200 字，完整内容保存在 `steps` 里。

## 五、面试可讲的点

### Q1：你的 Agent 怎么工作？

> 用 ReAct 循环：LLM 每轮输出一个 JSON 决策，要么调工具、要么给最终答案。代码解析 JSON，执行工具，结果喂回给 LLM，直到它说可以回答。
>
> 关键设计：
> - 最大轮次限制（6 轮）防死循环
> - JSON 强制输出，比自由文本好解析
> - 解析失败自动重试
> - 记录中间步骤，能看到 Agent 的思考过程
>
> 一个完整任务（搜索 + 匹配 + 追踪）走 4 轮。

### Q2：为什么手写 ReAct 不用 LangChain？

> LangChain 是黑盒，出问题难调试。手写一遍，每个环节都能讲清。
>
> 面试考"你理解 Agent 原理吗"，不是"你会用框架吗"。手写一遍，理解更深。工业界可以用框架，但底层机制必须懂。

### Q3：简历定制怎么避免造假？

> Prompt 明确禁止新增事实，只允许重排、重述。输出包含 changes（改了什么）和 warnings（哪些改不了）。
>
> 用户能看到改了什么，避免"AI 帮你造假"的风险。我理解 AI 内容生成的可信度是产品落地的前提。

### Q4：投递追踪为什么用状态机？

> 状态机能校验合法转换，防止数据脏。比如"被拒"不能直接变成"约面"。
>
> 同时支持统计：简历被看率、约面率。每次变更记录事件，能画完整时间线。
>
> 这是把业务流程建模为有限状态机，比用自由文本记录状态更可靠。

### Q5：你的系统架构是什么？

> 三层：
> - **RAG 层**：JD 知识库，语义问答
> - **Agent 层**：ReAct 循环 + 工具调用
> - **Dashboard 层**：Streamlit 管理界面
>
> 三种交互互补：
> - RAG 处理开放式问答（"哪些岗位要求 Python"）
> - Agent 处理多步任务（"帮我找北京岗位并匹配简历"）
> - Dashboard 处理结构化操作（批量标记、状态管理）

### Q6：你遇到过什么坑？

> 印象最深的是 **LLM 输出的 JSON 解析失败**。模型在长字符串里用了真实换行，导致 `json.loads` 报错。
>
> 我先在 Prompt 里明确要求"用 `\n` 转义"，再加 `json5` 兜底。改完后从"偶尔多走一轮"变成"稳定 2 轮完成"。
>
> 这让我理解：**LLM 输出格式不稳定是常态，必须设计容错机制**。

## 附录 A：开发中踩过的坑（Agent 相关）

### 抓取层

#### 1. 实习僧列表页字体混淆（PUA 码位）

- **现象**：列表页的 title/salary 是私有区码位乱码（如 `\uf71a\ue10a...`），DOM 里拿不到明文。
- **原因**：站点用动态 `@font-face` 渲染真实字符，字体里只有 PUA 码位，没有真实 cmap，无法还原。
- **修复**：**放弃列表页 title/salary，改成两段式**——列表页取 url/job_id/company/city，逐个访问详情页取明文 title/salary。
- **教训**：**抓取前先看渲染结果，不是看 DOM**。出现 PUA 乱码大概率是字体混淆，此时换页面（列表→详情）比破解字体更快。

#### 2. 关键词拆词匹配

- **现象**：搜"Agent 开发"命中"法律课程开发老师""F.A.M 厂牌助理（说唱）"等完全无关的岗位。
- **原因**：站点按词拆分匹配，含"开发"就命中。
- **修复**：抓完后增加相关性过滤——标题或正文含 Agent/LLM/大模型/RAG/智能体才保留。
- **教训**：**抓取量 ≠ 有效数据量**。抓取必须跟清洗过滤，42 条原始清洗后只剩 15 条。

#### 3. 字段分散在不同页面

- **现象**：列表页没有"发布时间"字段，无法做时间过滤。
- **原因**：站点只在详情页暴露刷新时间（`.job_date`）。
- **修复**：详情页抓取时一并抓时间，统一格式化为 `YYYY-MM-DD`。
- **教训**：**设计抓取器前先盘点"我需要的字段分别在哪"**。字段可能分散在列表页、详情页、甚至 API 响应里。

### Agent 行为层

#### 4. Agent 过度调用工具

- **现象**：单步任务"帮我找广州的 Agent 岗位"（预期只调 `search_jobs`），Agent 实际调了 `search_jobs` → `get_job_detail` → `match_resume`，共 3 次 / 4 轮。
- **原因**：System Prompt 没有"最小必要调用"的约束，模型倾向"多做一点显得更周到"。
- **修复**：待做（Round 2）。Prompt 里明确"只调用回答当前问题所必需的工具"。
- **教训**：**Agent 的"多做"不是优点**。过度调用浪费 token、增加延迟、引入错误。**Prompt 要写"最小必要原则"**。

#### 5. Mock 数据忽略了 keyword 参数

- **现象**：Agent 评估时，`_mock_search` 完全忽略 keyword，只按 city 过滤，"按关键词搜"的能力无法被测试。
- **原因**：mock 只有 3 条数据，作者简化实现时省掉了 keyword 匹配。
- **修复**：Agent 改用真实数据（`cleaned_jd.json`）后，keyword 在 title/description 中匹配。
- **教训**：**测试替身要保真**。Mock 简化可以，但必须保留被测接口的核心行为，否则评估结果无意义。

#### 6. 模块间数据源分裂

- **现象**：RAG 已切到真实数据（15 条广州 JD），Agent 搜索还在用硬编码 mock（3 条北京）——同句"找广州的 Agent 岗位"，RAG 能答，Agent 答不出。
- **原因**：模块间数据源没统一，各自用方便自己的。
- **修复**：`agent/tools/job_search.py` 和 `job_detail.py` 改成读 `rag/data/cleaned_jd.json`。
- **教训**：**模块间数据源要统一**。同一项目里不能有"一半 mock 一半真实"，否则任何测试结论都不可信。

### 测评层

#### 7. 评估集和数据源要同步

- **现象**：Agent 从 mock 切到真实数据后，评估集的 task 1/2/4/5/6 依赖"北京 + mock_001/002"，全部失效。
- **原因**：评估集和数据源没同步更新。
- **修复**：评估集任务全部改成广州 + 真实 job_id。
- **教训**：**评估集是数据的影子**。数据变了，评估集必须同步改，否则测的是过时的系统。

#### 8. 自动判定 vs 人工判定

- **现象**：DSH 为试跑方便加了 `--auto-judge` 开关（按"工具序列是否匹配"自动打分），和人工 y/n 判定可能不一致。
- **原因**：自动判定无法评估"答案质量"，只能评估"行为模式"。
- **修复**：`--auto-judge` 只作调试用，正式评估保持人工判定。
- **教训**：**自动评估能测流程，测不了质量**。LLM-as-Judge 可部分替代人工，但"是否真正解决问题"最终要人判断。

## 附录 B：与 AI（DSH）协作开发的经验

### 有效的 prompt 结构

1. **约束前置**：开头写"不改 `.env` / 不动 DB / 只改 X 文件"
2. **背景 + 任务**：让 AI 先读现有代码，再动手
3. **完成标准**：明确要求 git commit + 报告"改了什么 / 哪里不确定"
4. **禁止清单**：列清"不要做什么"

### DSH 的表现

- **强项**：反爬逆向、边界测试、发现隐藏依赖、自我修复 bug、诚实报告不确定点
- **弱项**：容易"顺手"改额外文件、会在 Prompt 外自加参数、改核心代码时风险高
- **最适合**：独立模块从零写、写测试、代码重构、找 bug
- **不适合**：改跨模块核心逻辑、需要人判断的商业决策

### 工程流程经验

- **一次一个任务**：太大 AI 迷路，太小浪费上下文
- **每任务一 commit**：出问题能回滚
- **每任务后审查 `git diff`**：看有没有"顺手改"的越界
- **push 前先看 `git log origin/main..main`**：避免 AI 顺手推掉未推送的提交
- **沙箱提权是常态**：D 盘写入、Playwright 启动会反复弹授权，这是环境限制不是 bug

### 三个反直觉的教训

1. **AI 说"已完成"不等于完成**——必须自己跑一遍验证
2. **AI 的"顺手改进"可能引入新坑**——超出清单的改动要单独审查
3. **AI 主动报告"不确定"时，认真读**——那往往是真问题

### 12. 新增工具后 Agent 的工具选择正确

- **测试**：给 Agent 新增 `update_tracking_status` 和 `delete_tracking` 后，在 Chainlit 里跑 3 个场景：
  1. "把我投的腾讯那条改成已约面" → 调 `update_tracking_status`，状态更新为 interview ✅
  2. "删掉阶跃星辰的投递记录" → 调 `delete_tracking`，记录删除 ✅
  3. "把所有投递记录都删了" → **不调工具**，说明"只能删单条" + 建议逐条删除 ✅
- **意外收获**：Agent 回答质量高——删除时主动提示"不可恢复"，批量删除时给了替代方案。
- **教训**：**工具描述决定了 Agent 的边界感**。在 `delete_tracking` 的工具描述里写了"一次只能删一家公司，不支持批量"，Agent 就正确拒绝了批量请求。**Prompt 工程不只是在 System Prompt，工具描述同样重要**。

### 13. 状态机放宽后用户体验改善

- **背景**：之前状态机严格（applied → viewed → interview → offer），用户说"我拿到 offer 了"会被拒。
- **修复**：改成"允许非终态跳到任意状态，终态不可变"。
- **验证**：本轮测试 `applied → interview` 直接成功（跳过了 viewed）。
- **教训**：**状态机的严格性是工程洁癖，用户体验优先**。真实用户不会按理想流程操作。


### 12. 上下文摘要的"条数计数"会切断工具调用配对

- **现象**：`compact_messages` 按消息条数截断，当 `MAX_HISTORY` 为奇数时，尾部第一条可能是"user: 工具返回结果"，它对应的"assistant: 工具调用"被切掉了。
- **原因**：ReAct 循环里 assistant 和 user(tool_result) 是成对出现的，按"条数"切割会破坏配对。
- **修复**：切尾部前检查——如果尾部第一条是 `user` 且 content 以"工具返回结果"开头，往前多保留一条。Round 4 修。
- **教训**：**上下文管理按"轮次"切割比按"条数"切割更安全**。成对出现的消息（assistant+tool_result）必须整体保留或整体丢弃。

### 13. 任务 prompt 可能基于过时的仓库状态

- **现象**：Round 3 的任务 3 要求"加 4 个统计卡片"，DSH 发现这 4 个卡片在我开始前就已提交（上上轮加的），我实际做的只是加转化率行。
- **原因**：写 prompt 时假设仓库还是上一轮结束时的状态，没有重新确认。
- **修复**：写 prompt 前先 `git log --oneline -5` 确认最新状态；或让 DSH 先读代码再判断"哪些已存在、哪些要新做"。
- **教训**：**Prompt 要描述"目标状态"，不要描述"当前状态 + 改什么"**。后者容易基于过时假设。让 AI 先读现状，自己判断怎么做。

### 14. 未提交的文件会被 DSH 看见但不动

- **现象**：Round 3 开始时 `agent/REFLECTION.md`、`applications.db`、`agent_results.json` 已是 modified 状态（本地手动改动），DSH 报告说"我没提交它们"。
- **原因**：DSH 遵守"只提交允许清单内文件"的约束，没顺手 commit。
- **修复**：手动处理（REFLECTION 和 results 提交，DB 不加）。
- **教训**：**每轮任务前先 `git status` 检查工作区**。如果有未提交的本地改动，要么先 commit，要么在 prompt 里明确"不要碰 X 文件"。

### 15. 流式接口默认不返回 usage

- **现象**：`chat_stream` 记录的 token 全是 0，标记 `stream_no_usage`。
- **原因**：OpenAI 兼容接口默认流式响应不带 usage，需要显式加 `stream_options={"include_usage": True}`。
- **修复**：加参数 + 兜底（网关不认时回退到原行为，不盲目重试）。
- **教训**：**"默认行为"往往不是"最优行为"**。流式为了低延迟省略了 usage，需要主动请求。任何 API 都要查文档确认哪些字段需要显式开。

### 16. 加新参数要考虑兼容性兜底

- **现象**：加 `stream_options` 参数后，如果网关不支持会报 400 或 TypeError。
- **修复**：DSH 写了 `_is_unsupported_param_error` 判定，只对"参数不支持"类错误回退重发；网络超时、鉴权失败直接抛出，不重试。
- **教训**：**加新参数时，要区分"可回退错误"和"不可回退错误"**。前者重试，后者抛出。否则重试会掩盖真实问题。

### 17. 沙箱限制是常态，不是 bug

- **现象**：DSH 每次写 D 盘、启动 Playwright、写 SQLite 都会弹授权。
- **原因**：项目在 D:\，DSH 工作区在 E:\，所有跨区写入都要提权。
- **教训**：**这是环境限制**，不影响代码质量。接受它，别试图绕过。

### 18. 没有 PDF 库时，不要只 raise

- **现象**：任务要求"reportlab 没有就用 fpdf2，都没有就 raise ImportError"。本机两个都没装。
- **DSH 的选择**：自己实现了一个标准库 PDF 写入器（TTF 解析 + 字形子集化 + Type0/CIDFontType2 + ToUnicode）。
- **验证**：用 PIL 对比字体子集化前后的渲染位图，**像素完全一致**。
- **代价**：约 390KB（子集化后仍需保留 cmap/hmtx/loca），排版朴素。
- **教训**：**"依赖没装"不是"做不了"的理由**。如果目标足够重要，用标准库也能实现。但要明确标注"这个分支没被验证过"，让用户知道边界。DSH 主动报告"reportlab/fpdf2 分支在本机完全没跑过"，这是诚实的体现。

### 19. 加新工具会改变 Agent 的既有行为

- **现象**：Round 5 往 TOOLS 加了 2 个工具（PDF 导出、投递包生成），System Prompt 里的工具清单变了。
- **潜在影响**：原来 10 题里可能有的题会调新工具；也可能因为工具变多，Agent 选择变分散。
- **修复**：跑一次全量评估，对比加工具前后。
- **教训**：**Agent 的"能力集"是一个整体**。加一个工具不是孤立改动，会改变所有既有任务的行为。每次扩展工具，必须回归全量评估。

### 20. 自动评估的一致性要用真实数据验证

- **现象**：`--compare` 可以同时跑人工和 LLM 判定，但非交互环境下的人工判定是"预设 y,y,y"。
- **DSH 的诚实**：主动指出"真正无偏的一致性统计还得你交互式跑一遍"。
- **教训**：**自动评估工具本身也要被评估**。用 LLM-as-Judge 时，不能只信它说"3 对 3 一致"，要人工抽检几条。

### 21. 子集化字体是 PDF 的核心难点

- **现象**：PDF 嵌入完整中文字体会导致文件 10MB+。
- **DSH 的做法**：解析 TTF，只保留文档实际用到的字形，重新构造 cmap 和 loca 表。
- **验证**：用 PIL 渲染对比，证明子集化没破坏字形。
- **教训**：**PDF 中文排版的核心是字体子集化**。要么用 reportlab 这类库搞定，要么自己啃 TTF 格式。这是很多"生成 PDF"任务的隐藏坑。

### 22. 评估任务间共享数据库会互相污染

- **现象**：任务 6 把"信投智联科技"加入追踪后，任务 7、8 查记录返回 3 条。Judge 预设只有 2 条，判定"第 3 条是编造"。
- **原因**：所有任务共享同一个 `test.db`，前一个任务的写操作污染后一个的预期。
- **修复**：每个任务独立数据库（或任务开始前重建）。
- **教训**：**评估任务要保证"独立可复现"**。共享状态会让"成功/失败"判定无法归因——你不知道是 Agent 错还是数据被污染了。

### 23. Agent 会宣称"已完成"但不验证

- **现象**：任务 10 里 Agent 调了 3 次 `delete_tracking`，直接宣称"已删除全部 3 条"。如果某次删除静默失败，它不知道。
- **原因**：Agent 没有"操作后验证"的习惯。
- **修复**：在 System Prompt 里加规则——**任何删除/修改操作后，用查询工具确认结果再报告**。
- **教训**：**"操作-验证"是 Agent 的可靠性关键**。宣称成功前必须有证据。这也是测试 Agent 幻觉的典型手段。

### 24. 评估集必须随能力集同步演进

- **现象**：第 10 题预期"系统没有删除工具"是 Round 2 之前写的。Round 2 加了 `delete_tracking` 后，这个预期失效，但没人改。
- **原因**：评估集不是代码，不会被"自动回归测试"覆盖。
- **修复**：每次扩展 Agent 能力后，**人工 review 评估集**——哪些预期过时了、哪些该新增。
- **教训**：**评估集是"活文档"**。能力扩展必须同步更新预期，否则测的是"过时的系统"。


### 25. Agent 的"操作-验证"必须写进工具描述

- **现象**：任务 10a Agent 删记录后多调了一次 `list_tracking` 复核。这**不是过度调用，是正确行为**。
- **修复**：在 `list_tracking` 工具描述里明确写"删除/改状态后用它复核，不要凭记忆答条数"。
- **教训**：**工具描述可以引导行为**。想让 Agent 做验证，不只是 Prompt 里说，**工具描述里也要强调**。工具描述是 Agent 每次决策都会看的信息。

### 26. 幻觉检测必须规则 + LLM 双保险

- **现象**：纯 LLM Judge 会漏检幻觉（比如 Agent 说"删了 3 条"但只调了 1 次 delete）。
- **修复**：规则版 `detect_hallucinations()` 只抓硬伤（宣称删除没调 delete、说 N 条但删 M 次、工具报错却说成功、条数与 list 不符），LLM 版做软判断。
- **教训**：**能用规则抓的幻觉，不用 LLM**。规则确定、无成本、无误判。LLM 只处理"语义级"的判断。

### 27. 账号配额是生产环境的隐形约束

- **现象**：Round 6 跑评估时第 9 题触发 429，因为账号模型配额用完。
- **原因**：火山方舟免费额度有限，测试频繁会快速耗尽。
- **修复**：轮换多个模型（不同模型独立额度）、用更便宜的模型做评估、缓存高频查询。
- **教训**：**AI 应用必须考虑成本控制**。不是"能调就行"，而是"每次调用花多少、用完怎么办"。

### 28. 评估任务必须独立数据库

- **现象**：Round 5 任务 6 写入后污染任务 7、8 的预期。
- **DSH 的选择**：**文件级隔离**（每个任务独立 `.db` 文件），而不是"删了重建"。
- **理由**：文件边界最硬——WAL 边车、残留连接都不会跨任务污染；跑崩时残留文件能直接打开排查。
- **教训**：**隔离粒度越粗越好**。同一个进程里"删了重建"不够硬，文件级隔离才彻底。


### 29. Judge 看到的是"截断后的 observation"

- **现象**：Round 6 加幻觉检测后，任务 3、4、5 被误判为"编造 JD 内容"。实际 Agent 输出的 JD 是真实的。
- **原因**：`react_agent.py` 记录 `steps` 时 `observation[:500]` 截断到 500 字。但完整 JD 可能 800+ 字，Judge 拿到截断版，看不到完整数据，就判定"Agent 编造了 observation 没有的内容"。
- **修复**：把 observation 截断限制放宽（2000 字），或让 Judge 拿完整版。
- **教训**：**评估工具依赖的数据，不能和展示用的数据混在一起**。截断是给人看的优化，但 Judge 需要原始数据。**日志要简洁，评估要完整——两者要分开**。

### 30. 批量操作前必须确认

- **现象**：任务 10b "删掉所有投递记录"，Agent 直接连删 2 条并宣称"已全部删除"。
- **原因**：System Prompt 没约束"危险操作前确认"。
- **修复**：Prompt 加规则——"删除/批量操作前，先向用户复述要做什么、涉及哪些记录，等确认再执行"。
- **教训**：**Agent 的"自作主张"在某些场景是危险**。删除、支付、发邮件这类**不可逆操作**，必须加确认步骤。这是 Agent 安全性的核心设计。

### 31. 评估集预期要和产品策略对齐

- **现象**：10b 的预期是"不应调用 delete_tracking"，但 Agent 分两次删除从技术上是可行的。
- **原因**：评估集写的是"理想策略"，Agent 做的是"可行策略"，两者不一致。
- **修复**：明确产品策略——"批量删除要先确认"，把这个写进 System Prompt 和评估集。
- **教训**：**评估集不仅测能力，也测策略**。当 Agent 行为和预期不符时，先问"哪个更对"，再改代码或改评估集。

### 32. 截断优化和评估工具是两件事

- **现象**：Round 6 加入幻觉检测后，任务 3/4/5 被误判为"编造 JD 内容"，实际 Agent 输出是真的。
- **根因**：react_agent 记录 steps 时 `observation[:500]` 截断，Judge 看不到完整数据。
- **DSH 的修复**：拆开——日志打印用 500 字，steps 存完整字符串，Judge 看 2000 字。**截断是给人看的优化，不是给评估用的压缩**。
- **教训**：**一个数字不能服务两种用途**。"日志简洁"和"评估完整"是两个目标，共用同一个截断值必然出错。

### 33. 加确认机制要同步改 Judge

- **现象**：System Prompt 加"危险操作前先确认"后，Agent 会先问"我将要删 X，确认吗？"，然后等用户回答。
- **新问题**：Judge 看到 Agent 没执行操作就说"没做完"，误判为失败。
- **DSH 的修复**：在 Judge prompt 里加"提问/征求确认不是事实陈述，不算幻觉"。
- **教训**：**改了 Agent 行为，必须同步 review 评估工具**。评估工具是 Agent 行为的镜子，行为变了镜子也要调。

### 34. 依赖第三方框架要注意版本兼容

- **现象**：`cl.Action` / `cl.user_session` 在 Chainlit 2.12 里不能用作类型注解，`import agent.app` 会直接报错。
- **DSH 的修复**：改成运行时引用。
- **教训**：**框架升级会静默破坏 API**。写代码时如果用到"版本敏感"的 API，加注释标注"适配 Chainlit 2.12"。

### 35. 账号欠费是 AI 项目的常见阻塞

- **现象**：Round 7 跑评估时，火山方舟返回 403 AccountOverdueError，所有 LLM 调用失败。
- **原因**：免费额度用完 = 账户欠费，不是"服务停止"。
- **应对**：充值 or 换平台（DeepSeek 官方 / 硅基流动 / 智谱）。
- **教训**：**AI 项目要有"模型切换"能力**。代码里 base_url 和 model 走环境变量，换平台只改配置不改代码。这是工程解耦的价值。

### 36. Judge 能识别"无依据的个性化推断"

- **现象**：任务 3 里 Agent 说"广州正好是你的目标城市"，Judge 判定这是"未经证实的个性化推断"，扣 5 分。
- **原因**：Agent 从 user_profile 读到"目标城市=广州"，所以回答里带了这句话。但 Judge 看不到 profile，只看到本次对话。
- **DSH 的判断**：属于"轻微瑕疵，不影响验收"，仍判成功。
- **教训**：**Judge 的上下文边界要明确**。个性化推断在真实产品里是加分（Agent 记住了用户），但 Judge 只看当前轨迹。要么把 profile 也塞给 Judge，要么接受这个扣分。**两种选择都是合理设计，关键要知道自己在选哪种**。

### 37. 确认机制生效后 Agent 更精简

- **现象**：Round 6 时任务 10a Agent 调 `delete_tracking + list_tracking` 两条；Round 7 只调 `delete_tracking` 一条。
- **原因**：System Prompt 加了"指名道姓只影响一条记录的操作可直接执行"，Agent 判断"删腾讯"不需要复核（单条操作、明确对象）。
- **教训**：**Prompt 规则会让 Agent 行为"分层"**。批量操作 → 确认；单条操作 → 直接执行。这种分层比"一刀切加确认"更贴合实际——用户不想为简单操作反复确认。

### 38. 100% 不代表完美，代表"评估集覆盖充分"

- **现象**：Round 7 跑到 10/10。
- **但要警惕**：100% 只能说明"Agent 在现有 10 题上表现完美"，**不能说明 Agent 已经"好用"**。
- **下一步要做的**：
  - **扩评估集**：加更多边界场景（多轮追问、异常输入、跨任务）
  - **真实用户试用**：3-5 个同学用一周，收集真实反馈
  - **Adversarial 测试**：主动尝试"骗" Agent（越狱、误导、冲突指令）
- **教训**：**评估集是"已知的已知"**。100% 说明你已知的场景都过了，但不代表未知场景也能过。**真实世界永远比评估集复杂**。

### 39. 给 AI 清理任务时要避免通配符

- **现象**：Round 8 收尾时 DSH 用 `Remove-Item "E:\deep seek harness\verify_*.py"` 清理临时脚本，结果误删了 5 个先前轮次创建的自测脚本。
- **原因**：通配符 `verify_*.py` 匹配了所有前缀是 verify 的文件，超出预期范围。
- **教训**：**给 AI 删除/清理类任务时，明确列出每个文件路径，不要用通配符**。或者明确说"只删这两个文件：X.py、Y.py"。这是 AI 协作的安全边界。

### 40. 增量入库的 id 设计决定能否识别"更新"

- **现象**：Round 8 加增量入库时，DSH 发现原 id 是 `chunk_0..chunk_N`（列表下标），无法区分"新增"和"修改"。
- **DSH 的修复**：id 改为 `chunk_<sha1(公司|岗位|chunk_index)>`——**不含正文**。这样改正文才能被识别为 `updated=1`（如果正文也算进 id，改正文会变成"新增 + 旧 id 变孤儿"）。
- **教训**：**增量系统的 id 设计要"稳定但不僵硬"**。稳定：换个表达方式不该变 id；僵硬：改内容应该更新而不是新增。这个平衡点是"key 描述的是实体（哪个岗位的第几块），不是内容（具体写什么）"。

### 41. 迁移旧数据要在切换前完成

- **现象**：Round 8 引入新的 id 格式后，现有 chroma_db 里的旧 id 会被增量逻辑当成"全部新增"，导致 34 次多余 embedding 调用。
- **DSH 的提示**：主动说"第一次直接跑 --incremental 会浪费 API"，建议先 `--rebuild`。
- **教训**：**引入"id 格式变更"这类 breaking change 时，必须提供迁移路径**。`--rebuild` 是简单粗暴但可靠的迁移方式。
