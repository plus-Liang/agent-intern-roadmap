# 项目复盘：求职助手 Agent

## 一、需求来源

我在找 Agent 开发实习，面临 4 个痛点：

1. **信息分散**：BOSS、实习僧各投一遍，没有统一视图
2. **匹配靠感觉**：投了才知道不合适
3. **简历重复改**：每个岗位手动调整，效率低
4. **进度难追踪**：投了 50 家，哪家看了全靠记忆

所以我做了这个 Agent：**把求职流程自动化，从搜索到追踪一站式完成**。

## 二、方案设计

### 整体架构

```text
用户输入
  ↓
ReAct Agent（LLM 自主决策）
  ├── 调 search_jobs → 岗位列表
  ├── 调 get_job_detail → 完整 JD
  ├── 调 match_resume → 匹配分数 + 差距
  └── 调 add_tracking → 加入追踪
  ↓
输出 + 状态保存
```

### 模块划分

| 模块 | 职责 |
|---|---|
| `tools_registry.py` | 工具注册中心，统一暴露能力 |
| `react_agent.py` | ReAct 循环 |
| `state_machine.py` | 投递状态定义 + 转换校验 |
| `storage.py` | SQLite 存储 |
| `tools/` | 具体工具实现 |
| `resume/` | 简历解析与定制 |
| `dashboard/` | Streamlit UI |

**为什么这样分**：

- **工具独立**：每个工具可单独测试，可替换实现（mock → 真实）
- **状态机独立**：转换规则可单元测试
- **Agent 独立**：换 Agent 框架不影响工具层

### 关键设计决策

#### 1. 手写 ReAct 而非用框架

**理由**：

- 面试考"你理解 Agent 原理吗"
- 手写一遍，每环节都能讲清
- 不依赖 LangChain 版本兼容

**代价**：代码多 100 行，需要处理 JSON 解析

#### 2. mock 实现 + 真实实现预留

**模式**：

```python
def search_jobs(keyword, city, limit, platform="mock"):
    if platform == "mock":
        return _mock_search(...)
    elif platform == "shixisang":
        return _fetch_from_shixiseng(...)
```

**为什么**：

- 先跑通链路，不被反爬卡进度
- 接口稳定，换实现只改一个函数
- 面试可讲"我先 mock 验证设计，后接真实平台"

#### 3. 可解释的匹配打分

**不给单一分数**，输出：

- 4 个维度分数（技能/经历/学历/城市）
- 差距列表
- 亮点列表

**为什么**：用户知道往哪优化，不是黑盒。面试时能讲"我设计的匹配算法有 4 个维度"。

#### 4. 简历定制不改变事实

**Prompt 明确禁止编造**，只允许重排、重述。输出包含：

- `changes`：改了什么
- `warnings`：哪些改不了

**为什么**：避免"AI 帮你造假"的风险。面试时能讲"我处理了 AI 内容生成的可信度问题"。

#### 5. 状态机 + 事件表

**投递状态**单独一张表，**事件历史**另一张表。

**好处**：

- 校验合法转换
- 支持统计
- 能画时间线

**面试可讲**："我用状态机管理投递流程，每次变更记录事件，能追溯完整历史。"

#### 6. SQLite 而非 JSON

**理由**：

- 投递记录会长到几百条
- 需要按状态查询
- 支持事件时间线

**面试可讲**："我用 SQLite 存投递记录，支持条件查询和事件追踪。"

#### 7. Chainlit + Streamlit 双 UI

**为什么两个**：

- **Chainlit**：对话式，适合"帮我找岗位"这种 Agent 交互
- **Streamlit**：表格化，适合"批量标记、查看列表"这种管理操作

**面试可讲**："三种交互方式互补：RAG 处理问答、Agent 处理多步任务、Dashboard 处理结构化操作。"

## 三、遇到的问题与修复

### 1. LLM 输出的 JSON 解析失败

**现象**：`json.loads` 报 `Expecting ',' delimiter`。

**原因**：模型在长字符串里用了真实换行。

**修复**：

- Prompt 明确要求用 `\n` 转义
- 加 `json5` 兜底

**效果**：稳定 2 轮完成，不再多走一轮。

### 2. 数据库表未建

**现象**：Dashboard 报 `no such table: job_marks`。

**原因**：`init_db()` 里没调用 `init_marks_table()`。

**修复**：补调用，删旧 DB 重建。

### 3. 状态机非法转换

**现象**：`update_status` 不校验，能把"被拒"改成"约面"。

**修复**：写入前 `validate_transition`，非法抛异常。

### 4. 简历匹配数据格式不统一

**现象**：`resume_json` 有时是字符串，有时是对象。

**修复**：工具里加 `isinstance` 判断。

### 5. Chainlit 步骤输出太长

**现象**：`cl.Step` 输出完整 JSON，屏幕被刷屏。

**修复**：截断到 200 字，完整内容保存在 `steps` 里。

## 五、面试可讲的点

### Q1：你的 Agent 怎么工作？

> 用 ReAct 循环：LLM 每轮输出一个 JSON 决策，要么调工具、要么给最终答案。代码解析 JSON，执行工具，结果喂回给 LLM，直到它说可以回答。
>
> 关键设计：
> - 最大轮次限制（6 轮）防死循环
> - JSON 强制输出，比自由文本好解析
> - 解析失败自动重试
> - 记录中间步骤，能看到 Agent 的思考过程
>
> 一个完整任务（搜索 + 匹配 + 追踪）走 4 轮。

### Q2：为什么手写 ReAct 不用 LangChain？

> LangChain 是黑盒，出问题难调试。手写一遍，每个环节都能讲清。
>
> 面试考"你理解 Agent 原理吗"，不是"你会用框架吗"。手写一遍，理解更深。工业界可以用框架，但底层机制必须懂。

### Q3：简历定制怎么避免造假？

> Prompt 明确禁止新增事实，只允许重排、重述。输出包含 changes（改了什么）和 warnings（哪些改不了）。
>
> 用户能看到改了什么，避免"AI 帮你造假"的风险。我理解 AI 内容生成的可信度是产品落地的前提。

### Q4：投递追踪为什么用状态机？

> 状态机能校验合法转换，防止数据脏。比如"被拒"不能直接变成"约面"。
>
> 同时支持统计：简历被看率、约面率。每次变更记录事件，能画完整时间线。
>
> 这是把业务流程建模为有限状态机，比用自由文本记录状态更可靠。

### Q5：你的系统架构是什么？

> 三层：
> - **RAG 层**：JD 知识库，语义问答
> - **Agent 层**：ReAct 循环 + 工具调用
> - **Dashboard 层**：Streamlit 管理界面
>
> 三种交互互补：
> - RAG 处理开放式问答（"哪些岗位要求 Python"）
> - Agent 处理多步任务（"帮我找北京岗位并匹配简历"）
> - Dashboard 处理结构化操作（批量标记、状态管理）

### Q6：你遇到过什么坑？

> 印象最深的是 **LLM 输出的 JSON 解析失败**。模型在长字符串里用了真实换行，导致 `json.loads` 报错。
>
> 我先在 Prompt 里明确要求"用 `\n` 转义"，再加 `json5` 兜底。改完后从"偶尔多走一轮"变成"稳定 2 轮完成"。
>
> 这让我理解：**LLM 输出格式不稳定是常态，必须设计容错机制**。
