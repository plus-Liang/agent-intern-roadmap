# RAG 工程决策复盘：为什么这样做

> 这份文档记录项目二里每一个"看起来理所当然"的技术选择，背后的权衡、代价和替代方案。
> 面试官会问"为什么"，这份文档帮你回答。

---

## 一、为什么用 Chroma，不用 FAISS？

### 三种常见向量库

| 向量库 | 特点 | 适合场景 |
|---|---|---|
| FAISS | Facebook 出品，纯 C++ 库，只做向量索引 | 需要极致性能、大规模向量 |
| Chroma | Python 原生，自带存储、元数据、过滤 | 原型开发、中小规模 |
| Milvus / Qdrant | 独立服务，支持分布式、高可用 | 生产环境、亿级向量 |

### 为什么选 Chroma

**理由 1：自带持久化**

FAISS 只管"向量索引"，不存原始文本、不存元数据。用它你要自己：
- 存原文（JSON、SQLite、内存）
- 存 metadata（岗位、公司、来源）
- 维护 id → 原文的映射

Chroma 一个 `collection.add()` 就全搞定。原型阶段，少写 100 行代码。

**理由 2：自带 metadata 过滤**

假设你要"只检索北京的岗位"，Chroma 一行：

```python
collection.query(
    query_embeddings=[vec],
    where={"city": "北京"},
    n_results=5
)
```

FAISS 做不到，得自己过滤。

**理由 3：规模够用**

FAISS 优势在百万级以上向量。你的场景 28–500 个 chunk，性能差异可忽略。

### 什么时候不该用 Chroma

- 向量超过 100 万：FAISS / Milvus
- 需要分布式：Milvus / Qdrant
- 需要高级索引（IVF、HNSW 调参）：FAISS

### 面试怎么答

> 我选 Chroma 是因为它自带持久化和 metadata 过滤，原型阶段能少写很多基础设施代码。FAISS 只做向量索引，原文和元数据要自己存，对原型不划算。如果向量规模超过百万级，我会换 Milvus 或 FAISS。

## 二、为什么 chunk_size 是 600，不是 300 或 1000？

### chunk 太小的代价

假设每段 100 字：

```text
Chunk 1：岗位职责\n1、参与大语言模型（LLM）应用、智能 Agent、工具调用工作流的研发落地
Chunk 2：结合业务场景完成功能迭代与效果优化
```

问题：
- **语义不完整**：一段话被切成两半，谁都不能独立表达完整意思
- **检索命中率下降**：Embedding 把 100 字转成一个向量，信息量太少
- **Top K 需要更大**：命中一个完整答案，可能要 10 个碎块拼起来

### chunk 太大的代价

假设每段 3000 字（一整条 JD）：

```text
Chunk 1：（包含公司、岗位、城市、职责、要求、加分项，共 1000 字）
```

问题：
- **向量被平均**：Embedding 把整段话"平均"成一个向量，"熟悉 Python"的权重被稀释
- **检索不准**：问"哪些岗位要求 Python"，可能命中讲"Python 优势"的无关段
- **token 浪费**：5 个 chunk 塞进 Prompt，大半不相关

### 600 字的来源

经验公式：

```text
chunk_size ≈ Embedding 模型的推荐长度 × 0.6
```

- OpenAI Embedding：推荐 512 token，约 800 中文字
- 火山方舟多模态：支持更长，但语义密度会下降
- 中文场景常用范围：**300–800 字**

**为什么是 600**：能包含 2–5 个完整句子，语义完整；信息密度高，不会被平均掉。

### 什么时候该调

| 场景 | 调整 |
|---|---|
| 问答短、答案具体（如"某岗位薪资多少"） | 调小到 300–400 |
| 需要跨段推理（如"对比多个岗位"） | 调大到 800–1000 |
| 文档段落长、结构少 | 加大 overlap |

### 面试怎么答

> chunk_size 是 RAG 最关键的参数之一。太小语义被切碎，太大向量被平均。我选 600，是因为中文句子通常 20–50 字，600 能容纳 5–10 句，语义完整。如果发现检索命中不准，我会先调这个参数，再调 Top K。

## 三、为什么 top_k 是 5，不是 3 或 10？

### 权衡

| Top K | 优点 | 缺点 |
|---|---|---|
| 3 | Prompt 短，生成快 | 召回率低，可能漏掉答案 |
| 5 | 平衡召回和成本 | 中庸选择 |
| 10 | 召回高，几乎不漏 | Prompt 长，token 成本高，噪音多 |

### 关键概念：召回率 vs 精确率

- **召回率**：该找到的有没有找到（Top K 越大越高）
- **精确率**：找到的有多少相关（Top K 越小越高）

**RAG 优先保召回**。因为：

- 召回不到 → 模型答不出，用户体验差
- 召回多了 → 模型能自己过滤，大不了回答"资料中没有"

### 什么时候调

| 现象 | 调整 |
|---|---|
| 模型经常说"资料中未找到" | 加大 Top K |
| 回答夹带无关内容 | 减小 Top K |
| token 花费太高 | 减小 Top K |

### 面试怎么答

> Top K=5 是召回和成本的平衡。RAG 系统里优先保召回，因为漏召回是硬伤，多召回模型能自己过滤。如果发现经常拒答，我会加大 Top K，再看效果。

## 四、为什么用模型判断相关性，不用距离阈值？

### 阈值方案的失败案例

你实际遇到的：

```text
问："哪个岗位对学历要求最低？"
命中距离：0.61–0.64
阈值：max_distance = 0.6
结果：全部过滤，返回"资料中未找到"
```

但模型看到这 5 条，能回答出"得物和屿智同行并列最低"。

**问题在哪**：阈值是"一刀切"，但"相关"是**语义判断**。

### 距离阈值的根本局限

距离反映"向量相似度"，不完全等于"语义相关"。

举例：

| 查询 | 命中内容 | 距离 | 实际相关 |
|---|---|---|---|
| 学历最低 | 5 条 JD 的学历要求 | 0.61 | 相关 |
| 会踢足球 | 5 条 Agent 岗位 | 0.74 | 不相关 |

0.61 和 0.74 只差 0.13，任何阈值都难分开。

**原因**：对比类问题（"哪个最低"）和无关问题（"会踢足球"），向量空间里的距离接近。

### 模型判断的优势

模型能看到：
- 问题意图：是"对比"还是"问事实"
- 片段内容：是 JD 职责还是 JD 学历
- 上下文关系：5 条片段能不能回答这个问题

它做的不是"距离比较"，而是"语义推理"。

### 设计原则

```text
检索层：负责召回，宁可多给，别漏
生成层：负责过滤，模型看完再决定
```

**别让检索层做过滤决策**——它视野太窄。

### 什么时候还用阈值

- 超大规模（10 万+ chunk）：初筛掉明显无关的
- 成本敏感：减少 LLM token 消耗
- 低延迟场景：先粗筛再精排

### 面试怎么答

> 我一开始用距离阈值过滤，结果"哪个岗位对学历要求最低"这种对比类问题被误杀。原因是阈值区分不开"对比类问题"（0.61）和"无关问题"（0.74）。后来我改成让模型判断相关性——检索层只负责召回，生成层负责过滤。这是 RAG 的分工原则：检索视野窄，生成视野全。

## 五、为什么用 API Embedding，不用本地？

### 本地 Embedding 的优势

| 维度 | 本地 |
|---|---|
| 成本 | 免费 |
| 速度 | 快（无网络延迟） |
| 隐私 | 数据不出本地 |
| 离线 | 可用 |

### 你的实际困境

Windows 11 智能应用控制拦截 `torch\lib\shm.dll`，报错：

```text
OSError: [WinError 4551] 应用程序控制策略已阻止此文件
```

试过：
1. 解除文件锁定：`Unblock-File` → 无效
2. 添加安全排除项 → 无效
3. 关闭智能应用控制 → 有风险
4. 虚拟环境重装 → 无效
5. 降级 PyTorch → 未测

### 决策：改 API Embedding

**为什么选择妥协**：

- 项目阶段：**目标是先跑通链路**，不是优化效果
- 时间成本：继续折腾 Windows 安全策略，可能 1 天都搞不定
- 换方案的代价：本地 → API，只改 `embedder.py` 一个文件

**牺牲了什么**：

- 费用：按 token 计费
- 速度：每次请求有网络延迟
- 效果：多模态模型做文本检索，不如专用文本模型

**得到了什么**：

- 项目推进：不卡在环境问题上
- 学习重点：关注 RAG 链路，而不是环境配置

### 工程思维的核心：有意识的权衡

**妥协 ≠ 失败**。关键是：

1. **知道自己在妥协什么**：不是"装不上就算了"，而是"明确知道 API embedding 比本地效果差"
2. **知道什么时候回来优化**：Day 11–12 会换回本地或换文本专用 API
3. **面试能讲清过程**：不是"因为我不会装"，而是"我评估了三个方案，选了最省时间的"

### 面试怎么答

> 我原本想用 BAAI/bge-small-zh 本地模型，中文效果好、免费。但 Windows 安全策略拦截了 PyTorch 的 DLL。我评估了三个方案：关安全策略（风险高）、换虚拟环境（试了无效）、改用 API embedding（牺牲效果但稳定）。我选了第三个，因为项目前期重点是跑通链路，效果优化留到后续。这是有意识的权衡，不是妥协。

**同样的经历，换个说法就是加分项。**

## 六、为什么用多模态模型（doubao-embedding-vision）做文本检索？

### 这不是最优选择

**最优**：`doubao-embedding-text-240715`（纯文本，支持批量）

**实际用的**：`doubao-embedding-vision-251215`（多模态，逐个请求）

### 为什么用了多模态

1. 你当时已创建了这个接入点
2. 想省一次控制台操作
3. 当时以为多模态"能处理文本，够用"

### 多模态的代价

| 代价 | 具体表现 |
|---|---|
| 速度慢 | 单次请求只能传 1 条，28 条要 28 次请求 |
| 效果差 | 文本检索距离 0.4–0.6，专用文本模型能到 0.2–0.3 |
| 维度高 | 2048 维（文本模型通常 1024 维），存储翻倍 |
| 贵 | 多模态按图片计费逻辑，通常比文本贵 |

### 什么时候真的需要多模态

- 检索对象包含图片（如产品图搜、视频检索）
- 需要"以文搜图"或"以图搜文"
- 跨模态对齐任务

**你的场景全是文本**，用多模态是"杀鸡用牛刀"，还拿错了牛刀。

### 面试怎么答（诚实版）

> 我一开始用了多模态 embedding，因为它是我已经创建的接入点，省事。跑通后发现两个问题：一是单次只能传一条，建库慢；二是文本检索的距离比专用文本模型高。所以后续优化会换回 `doubao-embedding-text` 或本地模型。**这是一个"先跑通再优化"的取舍**。

### 面试怎么答（更好版）

> 我评估过两种方案：多模态和文本专用。多模态支持跨模态检索，但单次只能传一条、距离偏高。文本专用模型支持批量、效果更好，但不能处理图片。我的场景是纯文本，所以理想选择是文本专用。我最初用多模态是因为接入点已存在，后来发现它不适合，这是"先跑通再优化"的取舍。

## 七、为什么每个 chunk 要带 metadata（company、title、city）？

### 表面原因：引用展示

模型回答时能说"来源：斯伦贝谢"，用户能核实。

### 深层原因：RAG 的可信度

**幻觉是 LLM 最大的问题之一**。RAG 的核心价值：

1. 让模型基于真实文档说话
2. 让用户能**验证**模型说的话
3. 出问题时能**追溯**是哪段资料错了

**没有 metadata，就没有追溯能力**。

### 一个真实场景

用户问："哪些岗位要求 Python？"

模型答："斯伦贝谢要求 Python。"

- **有 metadata**：用户点开"斯伦贝谢"链接，看到原文"熟练使用 Python"，确认无误
- **没 metadata**：用户只能信任模型，无法核实

### 面试怎么答

> 每个 chunk 都带 company、title、city 元数据，作用是：一是让回答能引用来源，二是让用户能验证，三是出问题能追溯。RAG 的核心价值不是"让模型知道更多"，而是"让模型说的话可验证"。

## 八、为什么有 metadata 过滤，但没用？

### 能力存在，场景未到

Chroma 支持：

```python
collection.query(
    query_embeddings=[vec],
    where={"city": "北京"},
    n_results=5
)
```

**为什么现在没用**：

- 你的 8 条 JD 覆盖北京、深圳、上海、长沙
- 用户提问没有明确"只要北京的"
- 加了反而限制召回

### 什么时候该用

| 场景 | 用法 |
|---|---|
| 用户明确"只看北京的岗位" | `where={"city": "北京"}` |
| 多用户共享知识库 | `where={"user_id": "xxx"}` |
| 数据有时间戳 | `where={"date": {"$gte": "2026-01-01"}}` |
| 需要排除某些来源 | `where={"source": {"$ne": "外部文档"}}` |

### 面试怎么答

> Chroma 支持 metadata 过滤，但现在场景不需要。如果用户说"只看北京的岗位"，我会在检索时加 `where` 条件。这个能力的价值在**多租户**或**有时间/类别限制**的场景，比如企业知识库要按部门过滤。

## 九、为什么用递归切块（splitter 按标题切），不用固定长度？

### 固定长度的失败案例

假设每 500 字切一刀：

```text
Chunk 1：
...岗位职责
1、参与 LLM 应用开发，包括
Chunk 2：
感知理解、任务规划、工具调用等模块...
```

**问题**：切在句子中间，"包括感知理解"被拆开了。检索时：
- 问"岗位职责是什么"：Chunk 1 只有半句
- 问"需要什么能力"：Chunk 2 只有半句

### 按标题切的好处

JD 天然有结构：

```text
【岗位职责】
1、参与 LLM 应用开发...
【任职要求】
1、硕士及以上学历...
```

按【】切，每块**语义完整**：
- "岗位职责"块：完整职责描述
- "任职要求"块：完整要求描述

**问"哪些岗位要求 Python"**：命中"任职要求"块，直接有答案。
**问"岗位做什么"**：命中"岗位职责"块，直接有答案。

### 递归切块的核心

**优先级**：

1. 先按大结构切（段落、标题）
2. 太长再按句子切
3. 还长再按固定长度切

**为什么叫"递归"**：一层不够，下一层继续。

### 面试怎么答

> 我用了按 JD 内部标题（岗位职责、任职要求）切块的方式。相比固定长度切块，好处是语义完整性高——"任职要求"里的 Python 要求不会被切到"岗位职责"块里。RAG 检索的准确性，很大程度取决于 chunk 的语义完整性。

## 十、为什么加 overlap（重叠）？

### 边界问题

假设：

```text
Chunk 1：A 岗位要求 Python、Java、Go
Chunk 2：熟练掌握 RAG、Agent 技术
```

如果原文是："A 岗位要求 Python、Java、Go、熟练掌握 RAG、Agent 技术"：

- 问"要求 Go 吗"：命中 Chunk 1 ✓
- 问"要求 RAG 吗"：命中 Chunk 2 ✓
- 问"要求 Go 和 RAG 吗"：**可能只命中一个**

### overlap 的作用

让相邻 chunk 有 80 字重叠：

```text
Chunk 1：A 岗位要求 Python、Java、Go
Chunk 2：Go、熟练掌握 RAG、Agent 技术   ← Go 重复出现
```

问"要求 Go 和 RAG"，两个 chunk 都能命中。

### 代价

- **存储增加**：28 个 chunk × 80 字 = 2240 字冗余
- **检索可能重复**：Top K 里可能有重复片段

### 什么时候不用

- chunk 之间本身有天然分隔（如每条 JD 独立）
- 存储成本敏感
- 使用父子分段（parent-child）

### 面试怎么答

> overlap 是为了避免"边界信息丢失"。如果两个相关句子被切在两个 chunk 里，检索时可能只命中一个。overlap 让相邻 chunk 共享一部分内容，提高召回。代价是存储和去重成本。

## 十一、为什么 Prompt 里要明确"只根据检索片段回答"？

### 不明确的后果

如果不加这句，模型会用**训练数据里的知识**补充回答。

问："哪些岗位要求 Python？"

模型可能答：
```text
常见要求 Python 的岗位有：
1. 后端开发
2. 数据科学家
3. AI 工程师
```

**全部是模型自己编的，不是你的 JD 库里的。**

### 明确约束后

```text
结论：以下岗位在 JD 片段中要求或涉及 Python：
1. 斯伦贝谢 | AI 实习生
2. 屿智同行 | Agent开发实习生
3. 腾讯 | 大模型算法

依据（岗位名 + 原文）：
- 斯伦贝谢：任职要求第2条："熟练使用 Python..."
```

**每个结论都有出处**。

### RAG 的核心约束

```text
RAG 的价值 = 大模型 + 外部知识 + 引用可验证
```

少了"引用可验证"，就退化成"大模型 + 幻觉"。

### 面试怎么答

> System Prompt 里必须明确"只根据检索片段回答"和"资料中没有就说资料中未找到"。不加这两条，模型会用训练数据编造答案，RAG 就退化成普通聊天机器人了。这是 RAG 和纯 LLM 的核心区别。

## 十二、工程思维的核心原则（总结）

### 1. 分层负责

```text
检索层：负责召回（宁多勿漏）
生成层：负责过滤（模型判断）
存储层：负责可追溯（metadata）
```

**不要让一层做超出它能力的事**。

### 2. 有意识的妥协

每个技术选择都有代价：

| 选择 | 代价 |
|---|---|
| 用 API embedding | 费用、速度 |
| 用多模态 | 效果、性能 |
| 用 Chroma | 不支持超大规模 |
| 用 Top K=5 | 可能漏掉长尾 |

**关键是"知道自己在妥协什么"，不是"不知道就妥协了"**。

### 3. 先跑通，再优化

```text
阶段 1：能跑（项目 2 Day 1–5）     ← 你在这
阶段 2：可展示（Day 6–10）
阶段 3：优化（Day 11–14）
阶段 4：可部署
```

**不要在阶段 1 纠结阶段 3 的优化**。

### 4. 面试讲"过程"不讲"结果"

面试官想听的不是"我做了 RAG"，而是：

- 遇到什么问题？
- 你怎么排查的？
- 为什么这样修？
- 有什么代价？
- 下一步怎么改？

**过程展示工程能力，结果只是副产品。**

## 十三、面试高频问题清单

| 问题 | 回答要点 |
|---|---|
| RAG 是什么？ | 检索 + 生成，让 LLM 基于外部知识回答 |
| 为什么不用纯 LLM？ | 幻觉、知识截止、无法引用 |
| chunk_size 怎么定？ | 语义完整性 vs 向量信息密度 |
| Top K 怎么定？ | 召回率 vs 成本，优先保召回 |
| 为什么阈值过滤不好？ | 对比类问题距离大，一刀切误杀 |
| Embedding 用什么？ | 本地免费但环境难，API 稳定但收费 |
| 怎么减少幻觉？ | 明确"只根据片段回答" + 引用原文 |
| 怎么评估 RAG？ | 5 类问题 + 准确率 + 失败分类 |
| 怎么优化 RAG？ | 切块 → Top K → Rerank → 模型选择 |
| 遇到过什么坑？ | Windows DLL 拦截、多模态接口不兼容、阈值误杀 |

## 附录：常用参数速查

| 参数 | 常见值 | 影响 |
|---|---|---|
| chunk_size | 300–800 | 语义完整性 |
| overlap | 50–150 | 边界信息保留 |
| Top K | 3–10 | 召回率 vs 成本 |
| Embedding 维度 | 512–3072 | 存储 vs 精度 |
| 距离阈值 | 0.4–0.7 | 精度 vs 召回 |

**记住：没有最优值，只有最适合当前场景的值。**
