# 项目复盘：岗位 JD 知识库问答

## 一、需求来源

我在找 Agent 开发实习，手头有 8 条目标岗位 JD。手动查询和比较效率低：

- 想知道"哪些岗位要求 Python"，要逐条读任职要求
- 想知道"哪个岗位薪资最高"，要手动翻 8 条头部
- 想知道"有没有远程实习"，要看每条 JD 的标签

所以我做了这个工具，核心目标：**把非结构化 JD 变成可检索、可比较的知识库。**

## 二、方案设计

### 整体架构

```text
用户问题
  ↓
Query Routing（LLM 分类）
  ├─ comparison → 结构化查询（JSON）
  └─ factual    → RAG
        ↓
    混合检索（BM25 + 向量）
        ↓
    RRF 融合（Top 12）
        ↓
    Reranker 精排（Top 5）
        ↓
    LLM 生成 + 引用
        ↓
    Chainlit 展示
```

### 模块划分

| 模块 | 职责 |
|---|---|
| `loader.py` | 读取 JD，按公司切分，提取元数据 |
| `splitter.py` | 按 JD 内部标题切块 |
| `embedder.py` | 文本转向量（API 调用） |
| `vector_store.py` | Chroma 建库和检索 |
| `retriever.py` | BM25 + 向量 + RRF 融合 |
| `reranker.py` | BGE Reranker 精排 |
| `generator.py` | 调用对话模型生成 |
| `rag_pipeline.py` | 主流程 + Query Routing |
| `evaluation/` | 评估集和脚本 |

**为什么这样分**：

- 每个文件只做一件事，出问题能快速定位
- 换 Embedding 只改 `embedder.py`
- 换向量库只改 `vector_store.py`
- 换 UI 只改 `app.py`

## 三、关键设计决策

### 1. 切块按标题，不按长度

JD 天然有结构：`【岗位职责】`、`【任职要求】`、`【加分项】`。

按标题切，每块语义完整：

- "岗位职责"块：完整职责描述
- "任职要求"块：完整要求描述

**对比固定长度切块**：固定 500 字可能把"熟悉 Python"和"掌握 RAG"切到两块，检索只能命中一个。

**面试话术**：chunk 的语义完整性，比 chunk 长度更重要。

### 2. 混合检索，不用纯向量

纯向量检索对**精确关键词**不敏感。比如搜"腾讯"，可能命中"字节"、"AI 公司"。

BM25 是关键词匹配，对精确匹配非常准。

**RRF 融合**：

- BM25 打分 0–50，向量距离 0–2，直接相加没意义
- RRF 只看排名，不依赖分数尺度
- k=60 是论文推荐默认值，不需调参

**面试话术**：混合检索是工业界 RAG 标配。BM25 补精确关键词，向量补语义理解。

### 3. Reranker 解决 Top K 矛盾

**Top K 小的代价**：漏掉排在 6-12 名但相关的 chunk
**Top K 大的代价**：噪音多，token 浪费，模型被干扰

**解法**：两阶段

- 混合检索宽召回 Top 12（宁多勿漏）
- Reranker 精排 Top 5（宁准勿多）

**Reranker vs 向量检索**：

- 向量检索：query 和 doc 分别编码，快但粗
- Reranker：query 和 doc 一起输入 Cross-Encoder，慢但准

**面试话术**：召回负责不遗漏，精排负责不冗余。这是工业界标准做法。

### 4. Query Routing：比较类问题不走 RAG

**RAG 的根本局限**：

- Top K 截断，看不全数据
- 语义检索不适合结构化字段提取

**"哪个岗位薪资最高"为什么 RAG 答不对**：

- 薪资在每条 JD 头部，8 条都要
- Top K=5 只返回 5 条
- 即使加大 Top K，模型在 24 条里找薪资再比较，噪音多易漏

**解法**：Query Routing

```text
问题 → LLM 判断类型
  ├─ comparison → JSON 查询 + 模板生成
  └─ factual    → RAG
```

**面试话术**：RAG 不是万能。比较/聚合类问题需要不同策略。这是 Agentic RAG 的核心思想——不同问题走不同路径。

### 5. 结构化答案用模板，不用 LLM

**踩过的坑**：一开始让 LLM 生成比较类答案，模型经常漏公司名：

```text
实际："学历要求最低的岗位是...那个职位（北京...）"
应该："得物App 学历要求最低，为「不限」"
```

**修复**：用模板拼字符串。

```python
FIELD_TEMPLATES = {
    "salary_max": "{company} 薪资最高，{salary_min}-{salary_max}/天",
    "days_per_week": "{company} 每周出勤要求最少，{days_per_week}天/周",
    ...
}
```

**原则**：结构化数据 → 模板；非结构化 → LLM。别让 LLM 做它不擅长的事。

### 6. Chainlit 而非 Streamlit

**Chainlit 的优势**：

- 内置对话历史（Streamlit 要手动管理 session_state）
- 内置引用展示（`cl.Text`）
- 内置流式输出（`stream_token`，比 `st.write_stream` 稳定）
- 支持步骤可视化（`cl.Step`）

**Streamlit 的坑**（项目一遇到）：

- 每次交互重跑整个脚本，DOM 冲突
- `st.write_stream` 和 `st.rerun` 组合触发 `removeChild`
- 追问框不显示（条件渲染问题）

**为什么不在项目二继续用 Streamlit**：Chainlit 更贴 RAG 场景，代码更少。

## 四、遇到的问题与修复

### 1. 本地 Embedding 被 Windows 拦截

**现象**：`WinError 4551 应用程序控制策略已阻止此文件`，`torch\lib\shm.dll` 加载失败。

**排查顺序**：

| 方案 | 结果 |
|---|---|
| `Unblock-File` | 无效 |
| Windows 安全排除项 | 无效 |
| 关闭智能应用控制 | 有风险，未做 |
| 虚拟环境重装 | 无效 |

**决策**：改用 API Embedding。

**权衡**：

- 牺牲：本地速度、隐私、免费
- 得到：稳定、不折腾
- 时机：项目前期重点是跑通链路，效果优化留到后续

**面试话术**：我评估了三个方案：关安全策略（风险高）、换虚拟环境（试了无效）、改用 API（牺牲效果但稳定）。我选了第三个，因为项目前期重点是跑通链路。这是**有意识的权衡，不是妥协**。

### 2. 多模态接口不兼容

**现象 1**：调用标准 `/embeddings` 报 400，模型不支持该接口。

**修复**：改用 `/embeddings/multimodal` 端点，输入格式改为 `[{"type": "text", "text": "..."}]`。

**现象 2**：`TypeError: string indices must be integers`。

**原因**：多模态返回 `{"data": {"embedding": [...]}}`，和标准的 `{"data": [{"embedding": [...]}]}` 不同。

**修复**：写 `_extract_embeddings` 兼容两种结构。

### 3. 切块从 8 到 28

**现象**：8 条 JD 只切出 8 个 chunk。

**排查**：

1. 看 `loader.py` 的切分逻辑
2. 发现问题：`re.split(r"-{10,}")` 把每条 JD 切成头部和正文
3. 过滤条件 `if "公司" not in block` 把正文块过滤掉了
4. 结果：每条 JD 只剩头部 200 字

**修复**：按 `【数字】公司：` 切分，保留完整正文。

**效果**：正文从 200 字恢复到 1000 字，chunk 从 8 增到 28。

**收获**：切块要基于文档结构，不能只看分隔符。

### 4. 头部元信息与正文冲突

**现象**：阶跃星辰头部"学历：不限"，正文"本科及以上"。

**第一次修复（失败）**：给所有头部加标记 `[网站元信息，仅供参考]`。

**结果**：准确率从 81% 降到 75%。原因：

- 薪资、城市字段本来就只在头部
- 标记后模型不敢用
- "哪个岗位薪资最高"变成"资料中未找到"

**第二次修复（成功）**：只对学历字段说"如冲突以正文为准"。

**收获**：修复问题要精准定位影响范围，不能一刀切。

### 5. Top K 截断

**现象**：问"哪个岗位薪资最高"，阶跃星辰（正确答案）没进 Top 5。

**排查**：

1. 单独测 retriever，阶跃星辰被召回
2. 但 `rag_pipeline.py` 里 `top_k=5`，截断了
3. Reranker 后仍排在 6 名外

**修复**：两阶段检索

- 混合检索 Top 12
- Reranker 精排 Top 5

**效果**：阶跃星辰进入 Top 5，薪资题答对。

### 6. RAG 不适合比较类问题

**现象**：无论怎么调参，"哪个岗位薪资最高"都答不对。

**根因**：

1. Top K 截断看不全数据
2. 语义检索不等于结构化字段提取

**解法**：Query Routing

- LLM 判断问题类型
- comparison 走 JSON 查询 + 模板生成
- factual 走 RAG

**效果**：对比分析类从 0/3 提升到 2/3。

### 7. 比较类答案缺公司名

**现象**：让 LLM 生成比较类答案，经常说"该岗位..."不点名。

**修复**：用模板拼字符串。

**原则**：结构化数据用模板，非结构化数据用 LLM。

### 8. Chainlit 不渲染 HTML

**现象**：`<details>` 标签被当纯文本显示。

**原因**：Chainlit 只渲染 Markdown，不渲染 HTML。

**修复**：改用 Markdown `>` 引用块。

### 9. 引用文本被 Markdown 误解析

**现象**：引用里的 `====` 被解析成 H1，字号突然放大。

**修复**：`re.sub(r"={3,}", "", text)` 清掉分隔符。

### Q1：你 RAG 怎么调的？

> 我的 RAG 经历了 6 轮迭代，准确率从 81% 到 87.5%。
>
> **核心改进**：
> 1. 混合检索：BM25 + 向量 + RRF，解决精确关键词漏召
> 2. Reranker 精排：从 Top 12 精排到 Top 5

> - LLM 生成比较答案会漏公司名
> - Top K 截断导致正确答案排在 6-12 名看不到

> RAG 最大的局限是**比较/聚合类问题**。因为它只能看 Top K 条，看不全数据；语义检索不适合精确字段提取。
>

>

### Q3：为什么用混合检索？

> 纯向量对精确关键词不敏感。搜"腾讯"可能命中"字节"。

## 附录：开发中踩过的坑（RAG 相关）

### 1. 分块策略：头部元信息独立成 chunk

- **现象**：真实 JD 接入 RAG 后，43 个 chunk 中有 15 个只有头部信息（公司/岗位/城市/薪资），没有正文。问"XX 岗位的职责是什么"，命中空壳 chunk，答不出内容。
- **原因**：`splitter.py` 按标题切块时，标题之前的元信息被当成独立一段，没和第一个正文块合并。
- **修复**：头部元信息合并到第一个正文段落。chunk 数从 43 降到 31。
- **教训**：**切块的语义完整性比块数更重要**。每个 chunk 应该是能独立回答某类问题的单元，不能让元信息和正文分离。

### 2. 段落别名不全导致漏切

- **现象**：TTC 用「职位描述」、滴滴用「任职资格（学历、目标院校…）」作段落标题，这两条 JD 无法被正确切分。
- **原因**：`SECTION_TITLES` 只覆盖标准写法，真实数据的标题千变万化。
- **修复**：补充「职位描述」「任职资格」「工作内容」「主要职责」等别名。
- **教训**：**真实数据比想象中多样**。规则引擎要留足够的兼容面，别假设数据都长成标准样子。

### 3. 删除数据前没查依赖

- **现象**：删掉 `rag/data/jd_structured.json`（旧 mock 残留）后，comparison 路由调用 `load_structured()` 抛 `FileNotFoundError`，"哪个岗位薪资最高"直接崩溃。
- **原因**：删除数据文件前没 grep 谁在依赖它。
- **修复**：`load_structured()` 加 try/except，找不到文件返回 `[]`；`handle_comparison()` 加"data 为空时降级走 RAG"。
- **教训**：**删数据 = 删代码**，删之前必须全仓库 grep 依赖。降级方案是兜底，不是补丁。

### 4. 模块级 import 是部署杀手

- **现象**：部署前发现 `rag_pipeline.py` 第 6 行 `from rag.reranker import rerank` 是模块级导入，而云端不装 `sentence-transformers`，即使 `USE_RERANKER=false`，`import rag.rag_pipeline` 也直接 `ModuleNotFoundError`。
- **原因**：`reranker.py` 顶部 `from sentence_transformers import CrossEncoder`，模块级导入把它拖进了整个导入链。
- **修复**：删掉顶层导入，保留 `_rag_answer` 函数内的懒加载。
- **教训**：**顶层导入 vs 懒加载要想清楚**。涉及重依赖（torch、transformers）的模块，一定用函数内懒加载，否则整个项目都被绑定。

## 附录 B：部署与工程化阶段踩过的坑

### 1. 覆盖式写入是数据丢失的常见原因

- **现象**：定时任务抓取后覆盖 `cleaned_jd.json`，把 15 条数据覆盖成 5 条。
- **原因**：`daily_job` 落盘时直接 `write_text(新数据)`，没读旧数据。
- **修复**：新增 `merge_jds(existing, new)`——读旧、去重、排序、写回。
- **教训**：**任何"更新数据"的场景，先问"是覆盖还是追加"**。定时任务、缓存刷新、日志写入都容易犯这个错。覆盖前必须显式确认"这是全量"还是"这是增量"。

### 2. 增量入库的 id 设计决定能否识别"更新"

- **现象**：原 id 是 `chunk_0..chunk_N`（列表下标），无法区分"新增"和"修改"。
- **修复**：id 改为 `chunk_<sha1(公司|岗位|chunk_index)>`——**不含正文**。改正文才能被识别为 `updated=1`。
- **教训**：**增量系统的 id 设计要"稳定但不僵硬"**。id 描述的是实体（哪个岗位的第几块），不是内容（具体写什么）。稳定：换表达方式不该变 id；僵硬：改内容应该更新而不是新增。

### 3. 迁移旧数据要在切换前完成

- **现象**：引入新 id 格式后，现有 chroma_db 里的旧 id 会被增量逻辑当"全部新增"，导致 34 次多余 embedding 调用。
- **修复**：先 `--rebuild` 一次性迁移，再启用 `--incremental`。
- **教训**：**引入 id 格式变更这类 breaking change 时，必须提供迁移路径**。简单粗暴但可靠的迁移是 `--rebuild`。

### 4. 给 AI 清理任务时要避免通配符

- **现象**：让 AI 清理临时脚本时用 `Remove-Item "verify_*.py"`，误删了 5 个先前创建的自测脚本。
- **原因**：通配符匹配范围超出预期。
- **教训**：**给 AI 删除/清理类任务时，明确列出每个文件路径，不要用通配符**。或者明确说"只删这两个文件：X.py、Y.py"。这是 AI 协作的安全边界。

### 5. 归档和删除是两个概念

- **现象**：90 天前的记录应该"退场"——是删除还是归档？
- **修复**：归档到独立文件，不是静默删除。
- **教训**：**"不再使用" ≠ "不再需要"**。归档保留追溯能力，也避免误删。判断标准：如果用户可能问"以前的 X 去哪了"，就需要归档而不是删除。

### 6. 边界数据要有保守设计

- **现象**：`cleanup_orphans(collection, valid_ids=[])` 如果字面执行，会清空整个库。
- **修复**：空集合时返回 0 不删。
- **教训**：**危险操作要设"默认拒绝"**。如果输入异常（空列表、None、非法值），宁可不执行也不要猜测。这是删库事故的常见根因。

### 7. Streamlit Cloud 的 Python 版本兼容

- **现象**：部署时报 `chainlit==2.12.0 需要 Python <3.14.0`，但云端是 3.14。
- **原因**：Streamlit Cloud 默认用最新 Python，锁定版本可能不兼容。
- **修复**：精简 `requirements.txt`（部署专用），去掉 chainlit、torch、pywin32 等云端不需要的包。
- **教训**：**本地环境 ≠ 云端环境**。要用单独的部署依赖文件，只装云端需要的包。

### 8. Secrets 配置要本地云端同步

- **现象**：本地 `.env` 换成 `glm-5-3-flash-260828`，但 Streamlit Cloud 的 Secrets 还是旧模型，导致云端 LLM 调用失败。
- **修复**：切换到新模型时同步改 3 处——本地 `.env`、`.env.example`、云端 Secrets。
- **教训**：**配置有"两处真相"时要同步**。本地开发方便，云端部署独立。任何敏感配置改动，都要检查两处。

### 9. Streamlit 1.63 的 st.html 是样式的正确注入方式

- **现象**：`st.markdown(unsafe_allow_html=True)` 注入 CSS 后，UI 时常抖动或丢失；`st.html("<style>...</style>")` 在 AppTest 里看不到元素。
- **原因**：1.63 里 `st.html` 是 CSS 注入的正确方式；AppTest 里 style 元素不进主树是**假阴性**。
- **修复**：改用 `st.html("<style>...</style>")`，真浏览器里完全可用。
- **教训**：**测试工具的"看不到"不等于"不存在"**。AppTest 简化了 DOM，样式类问题必须用真浏览器验证。

### 10. removeChild 的根因可能在样式注入方式

- **现象**：Streamlit Cloud 部署后前端报 `removeChild`，白屏。
- **排查**：本地无法复现，怀疑与 rerun 或 DOM 冲突有关。
- **修复**：改用 `st.html` 注入 CSS，问题消失。
- **教训**：**前端 bug 的"本地能跑"不代表云端能跑**。云端资源受限，DOM 渲染时序不同。要么用更稳的注入方式，要么降级 Streamlit 版本。

### 11. 部署时云端只读的文件系统

- **现象**：Streamlit Cloud 文件系统只读，SQLite 写入失败。
- **修复**：`APP_DB_PATH=/tmp/applications.db`，写临时目录。
- **代价**：重启后数据清空。
- **教训**：**免费部署平台的"文件系统"是临时的**。生产环境要用数据库（Supabase/Neon/Firebase）。Demo 用 /tmp 够用，但面试时要能讲清限制。

### 12. Hugging Face Spaces 的 Docker 转付费

- **现象**：准备部署 FastAPI + Chainlit 到 HF Spaces，发现 Docker/Gradio Space 都需要 PRO 订阅。
- **修复**：改用 Streamlit 原生组件复现对话功能，放弃 Chainlit 部署。
- **教训**：**免费服务会变**。做技术选型时留退路，比如：一个 UI 框架不够就换，不要把所有功能绑在单一平台上。

### 13. 上下文的"稳定前缀"决定缓存命中

- **现象**：每次对话都重新构造完整 system prompt（含用户偏好、简历），KV Cache 无法命中，成本高。
- **修复**：拆成 STATIC_PREFIX（角色 + 工具 + 规则，不变）+ DYNAMIC_CONTEXT（用户状态，走 user 消息）。hash 稳定后可命中缓存。
- **教训**：**上下文工程要从一开始考虑**。前缀越稳定，缓存命中越高，成本越低。

### 14. 工具调用要有运行时约束

- **现象**：Agent 可能连续重调同一工具，白烧完轮次。
- **修复**：给每个工具加 `risk_level`（read / reversible / irreversible）、`timeout`、`requires_confirmation`；`call_tool` 统一校验。
- **教训**：**Prompt 约束是软的，代码约束是硬的**。危险操作要靠代码强制确认，不能只靠模型"听话"。

### 15. 可观测性从第一天就要有

- **现象**：出问题后无法回答"这次运行用了多少 token？哪步最慢？哪个工具失败最多？"
- **修复**：加 `trace_id` + `log_event` 结构化日志（JSON 行）。
- **教训**：**print 是给开发看的，日志是给运维看的**。Agent 出问题的排查成本，取决于日志结构化的程度。

### 16. 假日志会误导诊断

- **现象**：看到日志里 Agent 连续 6 轮调 `list_tracking` 返回 `{"ok": true}`，判断为死循环 bug。
- **真相**：那是验证 `log_event` 埋点时手工写的自检样本，不是真实运行。铁证：6 轮时间戳只差 1.9ms、参数不合法、question 自称"自检"。
- **教训**：**"日志里看到异常"不等于"代码有 bug"**。诊断前先看日志是"哪个进程、哪次运行、什么上下文"写的。**先验证，再下结论**。

## 附录 C：Agent 开发核心踩坑（求职 Agent 项目）

> 从 24 条原始记录中筛出的 10 条，按 agent 开发视角排序，覆盖运行时、检索层、数据管道三类。

### 1. 工具失败要能自愈，但不能静默

- **现象**：夜间抓取任务 1 小时 42 分跑完，日志全是警告，数据 0 产出。
- **原因**：`_fetch_detail` 把异常吞成空 dict → `gather(return_exceptions=True)` 再吞一层 → `if all(errors)` 永远为假 → 自愈逻辑永不触发。
- **修复**：新增 `BrowserGoneError`（≥2 条才判定，单条不误判）；每批开跑前探活；一批全灭则重启浏览器重试一次。
- **教训**：**"异常被吞"比"异常抛出"更危险**。吞异常让自愈逻辑失效，让监控看到"成功但 0 条"。设计容错时，要区分"可恢复的失败"和"必须上报的失败"。

### 2. 对话历史要区分"单轮内"和"跨轮"

- **现象**：system prompt 承诺"岗位信息还在上文时直接列"，但每次追问都是失忆的。
- **原因**：`MAX_HISTORY` / `compact_messages` 只在**单轮 ReAct 内部**生效，跨轮不保留。
- **修复**：`sessions` + `messages` 表落库；`run()` 加 `history` 参数，`history=None` 时行为逐字不变。
- **教训**：**ReAct 循环内的消息压缩 ≠ 会话级历史**。两套机制都要有，生命周期不同。

### 3. 会话标识要用稳定键派生

- **现象**：真浏览器刷新（F5）后 thread_id 变化，追问答不出旧问题。
- **原因**：`user_session` 在刷新时重置，thread_id 每次重新生成。
- **修复**：thread_id 按 `user_id` 固定（`user:local`），刷新/重启都能续；New Chat 改用 `/history-clear` 重置而非换 id。
- **教训**：**会话标识不能依赖易失的 session 状态**。用稳定键（user_id）派生稳定 id，多用户时把 `local` 换成真实 user_id 即可，零返工。

### 4. 历史重放要区分"事实"和"状态"

- **现象**：每轮都有 resume/interview 动态上下文，如果历史里也存了旧状态，模型会看到两份冲突的状态。
- **原因**：历史注入和动态上下文都带状态信息。
- **修复**：`_history_to_messages` 只读 question/answer，动态上下文每轮现生成。
- **教训**：**用户问过什么（事实）要重放，用户当时的简历/面试状态（状态）不要重放**——状态每轮用最新的。

### 5. chunk metadata 必须携带业务主键

- **现象**：`retrieve()` 返回的 metadata 只有 company/title/city/chunk_index，拿不到 job_id，Agent 无法把 chunk 映射回结构化岗位。
- **原因**：`data_converter → loader → splitter` 三层都没透传 job_id，入库前就丢了。
- **修复**：`_META_FIELDS` 加 job_id/platform；**必须 `--rebuild` 全量回填**（增量补不回来，旧 chunk 全是孤儿）。
- **教训**：**RAG 的 metadata 设计要在建库前定死**。chunk 是检索单元，业务主键是映射锚点，两者必须在入库链路全程携带。漏一层，全量重建。

### 6. 检索层身份口径必须和数据层一致

- **现象**：chunk id 只用 `(company, title, chunk_index)` 时，两个平台的同名同司岗位会算出同一个 id 互相覆盖。
- **原因**：数据层身份是 `platform|job_id`，向量层身份必须同口径。
- **修复**：job_id 同时进 `_IDENTITY_FIELDS`，代价是旧 id 全变孤儿，由 `--rebuild` 的 `reset_collection()` 一次性换掉。
- **教训**：**不一致时，同实体在不同层有不同的"唯一性"，迟早撞车**。

### 7. 语义检索的入口不能用精确匹配的逻辑

- **现象**：模糊查询"想找偏大模型落地、能写工程代码的实习"走 semantic 分支，候选池为空，语义重排根本没机会跑。
- **原因**：`_semantic_probe()` 先把整句拆词再 `LIKE` AND 拼接，自然语言长句没有一条 JD 同时命中所有词。
- **修复**：改成抽短词做 **OR 召回**（`match_any=True`），再按 `job_id` 去重。
- **教训**：**AND 适合"已知关键词找岗位"，OR 适合"自然语言模糊需求"**。分流要发生在召回之前，不是重排之前。

### 8. 归一化越激进，误伤越大

- **现象**：折叠键剥掉"工程师/实习生/开发/算法"后，18 组里 16 组折的是**不同岗位**。百度北京"大模型算法"折进 3 个不同岗。
- **原因**：剥后缀后标题被削成"大模型/算法/java"这类**岗位类别词**，同公司同城常有多个不同岗位共用类别词。
- **修复**：折叠键退回原始 `(company, title, city)`，加"description 逐字一致"闸门。
- **教训**：**括号里 `(C++)(A193922)(高频交易)` 是区分信息，不是噪声**。宁可漏折，不可错折。

### 9. 门槛是平台相关的

- **现象**：`min_desc_len=200` 让 ncss 落盘率只有 34%（ncss 的 JD 普遍比实习僧短）。
- **原因**：同一指标在不同数据源上的分布不一样。
- **修复**：改成 per-platform 门槛，ncss=100，其他保持 200。
- **教训**：**一刀切会砍掉某个源的大部分数据**。清洗门槛要按平台配置。

### 10. 接口字段名 ≠ 字段语义

- **现象**：24365 的 `areaCodeName` 搜深圳返回"广东"（省级名称），直接存 city 字段会让广州/深圳都变"广东"，六城维度塌陷。
- **原因**：字段名看起来像"区域编码名称"，实际返回省级。
- **修复**：city 字段取**请求城市名**，不取接口返回的 `areaCodeName`。
- **教训**：**用之前必须实测几个值**。同理，`jobType=03` 看起来像"实习"，实际丢 30% 数据——不要信参数的"字面含义"。
